## 1. Загальна картина

Задача пріору — до всякого навчання, **суто з геометрії й кольору**, прикинути для кожної точки:
«наскільки схоже, що тут відбулася зміна?». Це число потім і підказує мережі, де дивитись уважніше.

На вході дві хмари: `data0` (до) і `data1` (після). Фічі кожної точки — `x = [ones, R, G, B]`
(`FEAT: 3` у конфізі → 4 канали; канал 0 — константні одиниці, канали 1-3 — колір).

### Крок 1 — зіставити точки між хмарами

```python
nn_list00 = knn(data1.pos, data0.pos, 1, data1.batch, data0.batch)   # forward:268
```

Для кожної точки `data0` шукається найближча точка в `data1`. Далі те саме в зворотний бік
(`nn_list10`) — усе рахується симетрично, окремо для кожної хмари.

### Крок 2 — два незалежні сигнали про зміну

Обидва рахуються в `get_mask_v2` (рядки 416-433) і обидва нормовані в `[0, 1]`, де 0 = «без змін»,
1 = «точно зміна»:

| | Що це | Формула | Поріг |
|---|---|---|---|
| **D** | геометрична відмінність | `min(dist / pos_th, 1)` | `pos_th = 3.0` м |
| **C** | колірна відмінність | `min(abs(mean(ΔRGB)) / f_th, 1)` | `f_th = 0.6` |

Пороги — хардкод-літерали в `forward()` (рядки 261-262), не в конфізі. Звідки взялися саме ці
числа — розділ 2.

`dist` — відстань від точки до її найближчого сусіда в іншій хмарі. Після `GridSampling3D(size=1.0)`
сусіди зазвичай за 0-1.5 м, тож D реально гуляє десь у `[0, 0.5]`.

`ΔRGB` — різниця кольору з тим самим найближчим сусідом. RGB у пайплайні **вже нормалізований** у
`[0, 1]` (це підтверджено runtime-діагностикою в аудиті; рання гіпотеза про 0-255 спростована).

### Крок 3 — злити два сигнали в один

```python
input = 0.5 * pos_m_1 + 0.5 * f_m_1   # = 0.5·D + 0.5·C
mask = input                           # той самий тензор, не копія
return input, mask
```

### Крок 4 — використати результат двічі

```python
data0.x[:, 0] = input0.squeeze(-1)     # forward:276 — ones-канал переписується на p
data0.mask = mask0                     # forward:273
...
data0.x = self.self_att_list[0](data0.x, None, False, mask0)   # forward:292
```

Тобто одне й те саме число `p`:

1. **стає вхідною фічею** — займає канал 0 замість марних одиниць, і перший KPConv-блок бачить
   `[p, R, G, B]`;
2. **керує attention-шаром** на кожному рівні енкодера (що саме воно там робить — розділ 5).

`input` і `mask` — буквально один об'єкт, ніякої різниці між ними немає.

### Крок 5 — той самий ланцюг, але як C++

Torch-код `get_mask_v2` (рядки 416-433) читається важко не через математику, а через **боротьбу з
формою тензора**: `reshape`, `unsqueeze`, `repeat`, `mean(dim=-1)` існують лише для того, щоб один
векторний вираз обробив усі N точок без циклу. Якщо переписати ланцюг явним циклом, уся ця
машинерія зникає — лишається чиста арифметика:

```cpp
using Vec3 = std::array<float, 3>;

// pos_1, pos_2 : позиції точок хмар «до» і «після», розмір N
// f_1,   f_2   : колір (RGB) тих самих точок,        розмір N, вже нормований у [0,1]
// neigh_idx    : neigh_idx[i] = індекс точки в хмарі 1, найближчої до точки i хмари 2
//                (це рядок 1 з knearest_idx_2 — вивід torch_geometric.nn.knn)
std::vector<float> get_mask_v2(
        const std::vector<Vec3>& pos_1, const std::vector<Vec3>& pos_2,
        const std::vector<Vec3>& f_1,   const std::vector<Vec3>& f_2,
        const std::vector<int64_t>& neigh_idx,
        float pos_th /* = 3.0f */, float f_th /* = 0.6f */)
{
    const size_t N = pos_2.size();
    std::vector<float> p(N);

    for (size_t i = 0; i < N; ++i) {
        const int64_t j = neigh_idx[i];          // сусід точки i у хмарі 1

        // --- геометрична відмінність -> D ---
        float dx = pos_2[i][0] - pos_1[j][0];
        float dy = pos_2[i][1] - pos_1[j][1];
        float dz = pos_2[i][2] - pos_1[j][2];
        float dist = std::sqrt(dx*dx + dy*dy + dz*dz);
        float D = (dist > pos_th) ? 1.0f : dist / pos_th;      // clamp(dist/pos_th, 0, 1)

        // --- колірна відмінність -> C ---
        // ВАЖЛИВО: mean по каналах від ЗНАКОВОЇ різниці, і лише потім abs (див. розділ 6)
        float dmean = ((f_2[i][0] - f_1[j][0]) +
                       (f_2[i][1] - f_1[j][1]) +
                       (f_2[i][2] - f_1[j][2])) / 3.0f;
        float cdiff = std::fabs(dmean);
        float C = (cdiff > f_th) ? 1.0f : cdiff / f_th;        // clamp(|mean(dRGB)|/f_th, 0, 1)

        // --- фьюжн 50/50 ---
        p[i] = 0.5f * D + 0.5f * C;
    }
    return p;   // Python повертає (input, mask) — той самий об'єкт двічі
}
```

## 2. Звідки взялися пороги `pos_th = 3.0` і `f_th = 0.6`

У репозиторії — жодного сліду: ні конфіга, ні скрипта, ні коментаря. Відповідь у статті
([IEEE TGRS 2024](https://ieeexplore.ieee.org/document/10620319/)):

> The average distance of SLPCCD, HKCD and URB3DCD-V2 is 0.15, 1.5 and 1.8, so the distance
> thresholds are set to 0.3, 3.0 and 3.6. The average texture difference of SLPCCD and HKCD is 0.3
> and 0.3, so the texture thresholds are set to 0.6. For URB3DCD-V2, because there are not colors in
> the datasets, the color weight is set as 0 and the texture weight as 1.

### Правило: поріг = 2 × середнє по датасету

| Датасет | сер. відстань | `pos_th` | сер. різниця текстури | `f_th` |
|---|---|---|---|---|
| SLPCCD | 0.15 | 0.3 | 0.3 | 0.6 |
| **HKCD** | **1.5** | **3.0** | **0.3** | **0.6** |
| URB3DCD-V2 | 1.8 | 3.6 | — (немає кольору) | — |

Сенс: `D = dist / (2·mean_dist)`, отже при `dist = mean` виходить `D = 0.5`. Пороги навмисне
підібрані так, щоб **середня точка датасету відображалась рівно в середину діапазону пріору**.

### Але заміряні дані з цим не сходяться

Якщо `pos_th = 2 × 1.5`, то `D.mean` мав би бути **0.5**. Runtime-таблиця аудиту дає **0.22-0.33**.
Те саме з кольором: за правилом `C.mean = 0.5`, заміряно **0.30**.

Обидва промахнулись приблизно вдвічі й **в один бік**. Найімовірніша причина: середні зі статті
рахувались на сирих хмарах і/або по всьому датасету, а модель бачить дані вже після
`GridSampling3D(size=1.0)` і нарізки на циліндри. Тобто калібрування зроблене не на тому розподілі,
який реально доходить до `get_mask_v2`.

Для baseline це майже безболісно: `p` просто живе в нижній половині діапазону, лишаючись лінійним і
монотонним (розділ 4). Для uncertainty-варіанту — критично, див. виноску нижче.

> **Чому це вбиває inverse-variance фьюзію.** Бернуллієва дисперсія `σ² = p(1−p)` має похідну
> `1 − 2p`, яка в точці `p = 0.5` дорівнює **нулю**. Тобто 0.5 — це одночасно точка максимуму
> дисперсії (0.25), мінімуму ваги (`w = 1/σ² = 4`) і **стаціонарна** точка, біля якої дисперсія
> майже пласка.
>
> Правило статті навмисне садить **обидва** пріори рівно в 0.5 — тобто точно туди, де їхні ваги
> максимально низькі, рівні між собою і нечутливі до значення. Наслідок: `w_D ≈ w_C` →
> `μ ≈ (D+C)/2` → **inverse-variance фьюзія вироджується назад у baseline за побудовою**.
>
> Це не гіпотеза, а арифметика. На заміряних середніх (`D=0.25`, `C=0.30`):
> `w_D = 5.33`, `w_C = 4.76` → `μ = 0.2736`, тоді як baseline дає `0.275`. **Різниця 0.002.**
>
> І порогами це не лікується: підняти поріг → `p→0` → `σ²→0` → джерело починає домінувати,
> голосуючи «без змін»; опустити → `p→0.5` → вироджуємось у 50/50. Оскільки `σ²` є функцією
> **самого значення**, будь-який поріг нерозривно задає і «де сидить оцінка», і «наскільки їй
> вірити». Пороги — не той важіль; дефект структурний.

> ⚠️ **Статус джерела:** PDF відкрити не вдалось (ResearchGate → 403, IEEE → пейвол). Цитата взята
> з пошукового індексу RG-сторінки й відтворилась ідентично у двох незалежних запитах; числа 3.0/0.6
> точно збігаються з кодом, а деталь про URB3DCD (`colour weight = 0`) у нашому коді відсутня — тож
> це не схоже на артефакт. Якщо буде доступ до PDF — звірити розділ з параметрами.

## 3. Головне: 50/50 — це не «довільний компроміс»

Байєсівське зважування двох шумних оцінок (inverse-variance weighting) виглядає так:

```
μ = (w_D·D + w_C·C) / (w_D + w_C),   де   w = 1/σ²
```

Ідея: чим менша похибка джерела (σ²), тим більша його вага. Тепер підстав `σ_D = σ_C` — ваги стають
рівними, і формула **точно вироджується в** `(D + C)/2`.

Тобто **baseline уже є байєсівською фьюзією** — за припущення «обидва джерела однаково надійні».
Це не «наївний фікс, який ми покращуємо байєсом». Наш підхід не додає байєсівськість, він лише
**послаблює припущення про рівну надійність**, намагаючись оцінити σ² з даних.

Уся суперечка зводиться до одного питання: чи є `p(1−p)` чесною оцінкою *відносної надійності*
джерела? (Спойлер: ні — але це тема аудиту.)

## 4. Властивості baseline

### 4.1. Помилка ділиться навпіл

`p = (D + C)/2` — це просто **середнє**. Тому:

```
D=0.2, C=0.6                     →  p = 0.4
D зсунувся на 0.2 (став 0.4)     →  p = 0.5
```

D зсунувся на 0.2 → p зсунувся на 0.1. **Рівно половина.** І так завжди, за будь-яких D і C.

Формальний запис `∂p/∂D = 0.5` означає рівно це: «наскільки зсунеться p, якщо посунути D». Тут це
0.5 і ніколи не змінюється.

**Практичний сенс:** якщо один із двох пріорів збрехав — брехня входить у результат наполовину,
ніколи більше. Жодне джерело не може перетягнути ковдру на себе.

> Це та точка, де uncertainty-варіант відрізняється принципово: там це число **не константа** і може
> підповзати до 1, тобто одне джерело здатне забити інше повністю.

### 4.2. Без сюрпризів (монотонність)

Більше D → більше p. Більше C → більше p. Завжди. Не буває так, що ти збільшив геометричну
відмінність, а пріор зміни *впав*.

### 4.3. Формула ніде не ламається

`(D + C)/2` рахується для будь-яких D і C, ділення на нуль немає. (У формулі uncertainty-варіанту —
є: `0/0` при `D=1, C=0`.)

### 4.4. Де сидить і як гуляє

- `p.mean ≈ 0.28` — типове значення пріору
- `p.std ≈ 0.14` — гуляє приблизно ±0.14 навколо цього

Пораховано з runtime-таблиці аудиту (`D.mean ≈ 0.25`, `C.mean ≈ 0.30`, `D.std ≈ 0.19`,
`C.std ≈ 0.21`) за формулою `p.std = sqrt(0.25·σ_D² + 0.25·σ_C²)`, у припущенні незалежності D і C.

**Навіщо це рахувалось:** якби `μ` uncertainty-моделі майже не гуляла (std ≈ 0), це означало б
«константа замість сигналу» — гіпотеза «мертвих каналів» з аудиту. Але вона гуляє на 0.13-0.27, а
baseline — на ~0.14. Приблизно однаково, тож цією метрикою uncertainty-варіант не звинуватиш.

## 5. Що `mask` реально робить — і це не те, що написано в назвах

### 5.1. Спершу про softmax

`softmax` перетворює список чисел на частки, які в сумі дають 1. Більше число → більша частка:

```
softmax([2, 1, 0])  =  [0.67, 0.24, 0.09]     ← перший канал забирає дві третини
```

### 5.2. Тепер фокус

`Attention.forward` (рядки 447-468):

```python
energy = self.energy_conv(value)            # (N, C)
if mask is not None:
    energy = torch.multiply(energy, mask)   # (N,C) * (N,1) → broadcast
attention = self.softmax(energy)            # nn.Softmax(dim=-1)
x_r = torch.multiply(value, attention)
```

Пріор множить числа **перед** softmax. Ті самі числа, змінюється лише множник:

```
p = 1.0:   softmax([2, 1, 0])        = [0.67, 0.24, 0.09]   ← різко, є фаворит
p = 0.28:  softmax([0.56, 0.28, 0])  = [0.43, 0.32, 0.25]   ← майже порівну
p = 0.0:   softmax([0, 0, 0])        = [0.33, 0.33, 0.33]   ← ідеально порівну
```

**Малий `p` розмазує, великий `p` загострює.** Цей множник-регулятор різкості називають
«температурою» (термін позичений з фізики, глибокого сенсу тут нема).

Тому «маска гейтить attention» — **неточне** формулювання. Нічого не *зануляється*. Пріор керує тим,
**наскільки рішуче** шар обирає фаворита: очікуємо зміну → дозволяємо обирати різко; не очікуємо →
змушуємо розмазати все порівну.

При `p.mean ≈ 0.28` типова температура доволі висока, тобто гейт загалом працює м'яко.

### 5.3. І це взагалі не self-attention

Справжній self-attention — це коли кожна точка дивиться на всі інші й вирішує, кого слухати
(матриця «хто на кого дивиться» розміром N×N).

Тут такої матриці **немає**. Тензори — `(N, C)`, точки × фічі (partial-dense формат, батч живе в
`data.batch`). `softmax(dim=-1)` іде вздовж **каналів**, а не вздовж точок. Кожна точка обробляється
сама по собі, а softmax обирає між **її власними фічами**.

Питання не «кого з сусідів слухати», а «яка з моїх власних фіч важлива».

> Назва `self_att_list` і коментарі `# b, n, c` / `# b, c, n` всередині `Attention` — рудименти від
> версії з батч-вимірами. Вони брешуть, не ведись.

## 6. Побічне спостереження: `C` — це не колірний пріор

```python
f_mat_2 = torch.abs(torch.mean(f_2_ex - nearest_f_2of1, dim=-1).view(-1, 1))   # рядок 428
```

Спершу `mean` по каналах від **знакової** різниці, і лише потім `abs`. Протилежні зміни каналів
**взаємно гасяться**:

```
(1, 0, 0) → (0, 1, 0)     mean(-1, +1, 0) = 0     →  C = 0, «колір не змінився»
```

По суті `C ≈ |Δяскравість|`, і будь-яка зміна відтінку за сталої яскравості для нього невидима.
Було б `mean(abs(...))` або норма — була б справжня колірна відстань.

Це присутнє і в baseline, і в uncertainty-варіанті однаково, тож саме порівняння між ними не ламає.
Але з inverse-variance фьюзією воно взаємодіє значно гірше — див. аудит.

## 7. Увесь конвеєр на одній сторінці

Шпаргалка: словами коротко, формулами просто. Формули — для однієї точки, якщо не сказано інше.

### 7.1. Вхід

```
x = [p, R, G, B]            # baseline;  p = 0.5·D + 0.5·C
x = [μ, R, G, B, σ²]        # uncertainty-варіант (див. prior_mask_math_uncertainty.md)
```

Пріор рахується **до мережі**, з сирих даних:

```
D = min(dist/3.0, 1)                 # геометрія: відстань до сусіда в іншій хмарі
C = min(|mean(ΔRGB)|/0.6, 1)         # «колір» (насправді яскравість — розділ 6)
mask = p                              # baseline
mask = conf·μ + (1−conf)·0.5          # uncertainty;  conf = 1 − σ²/0.25
```

### 7.2. Згортка (KPConv) — єдине місце, де точки спілкуються

```
x' = Σ_сусіди  w(відстань до сусіда) · W · x_сусіда
```

Точка збирає фічі з околу; на виході 64+ каналів навчених ознак. Рівень за рівнем хмара
проріджується, канали ростуть.

### 7.3. Гейт («attention») — тут і енергія, і маска

```
e = W_e · x                     # ЕНЕРГІЯ: навчений шар виставляє бал кожному каналу
e = e · mask                    # маска (скаляр точки) стискає всі бали
a = softmax(e)                  # бали → частки, Σa = 1
x_r = (W_v · x) ⊙ a             # канали × свої частки: фаворити пройшли, решта придушена
x = x + f(x_r)                  # residual: сирий вхід + поправка
```

«Енергія» — просто назва логітів (сирих балів до softmax) в attention-літературі, спадок від
energy-based моделей; фізики тут немає — це вихід звичайного лінійного шару. Маска працює
температурою: `mask=1` — відбір каналів різкий, `mask→0` — частки рівні, поправка знеособлюється
(розділ 5). Softmax по **каналах точки**, не по точках — тому це гейт, а не self-attention.

### 7.4. Порівняння хмар — на кожному рівні

```
diff = x⁰ − x¹[nn]              # фічі точки мінус фічі її сусіда з іншої хмари
x = concat(x, diff)             # і те, й різниця йдуть далі
stack.push(diff)                # різниці відкладаються для декодера
```

### 7.5. Декодер і голова

```
x = upsample(x) + stack.pop()   # U-Net: підйом роздільності + різниці свого рівня
out = softmax(FC(x))            # клас на точку: без змін / new / demolished
```

### 7.6. Лосс

```
loss = NLL(out⁰, y⁰) + NLL(out¹, y¹)     # обидві хмари; маска в лоссі не бере участі
```

**Одним реченням:** пріор рахується з сирих даних ще до мережі, входить двічі — каналом на вході й
температурою гейта на кожному рівні енкодера; мережа вчиться на різницях фіч між хмарами, а маска
лише регулює, наскільки різко кожна точка виділяє власні канали.
